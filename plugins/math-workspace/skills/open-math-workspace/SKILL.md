# Open Math Workspace

Use this installed Codex plugin as the runtime and generic-skill provider for Codex projects. Reuse its CLI/launcher for initialization, preparation, finalization, export, and Lean commands. Keep project configuration, manuscripts, review records, and project-specific rules in the project; do not copy the runtime into `tools/math-workspace`, add a second npm installation, or embed generic skill copies merely to use this plugin. Independent non-Codex users can use the standalone CLI/npm path described in the installation guide.

Use `open_reader` to read, inspect, or navigate local Markdown or a prepared Math Workspace project beside the current conversation. Use `open_workspace` for the standalone project entry. When discussing a quoted selection, read the inline Markdown attachment and its source location; use the original file when more context is needed.
- The plugin also registers the native Markdown file viewer: choosing Math Workspace from a file context menu or preview viewer menu opens the current conversation's side panel. Do not install the legacy external `codex-handler` unless the user requests a browser or an older host requires it.
- Pass the explicitly chosen Markdown file or current local project folder. Valid `.math-workspace/config.json` enables workspace tools; without it, the Reader uses lightweight reading mode.
- Pass a project-relative `pagePath` when the user identified a chapter to open.
- If no current local context is available, call the tool without a root to use the local chooser. Reading mode never initializes a project, scans formal objects or starts Lean, audit, Git-diff or publication operations. A damaged configuration is shown explicitly; the user can choose reading-only fallback.
- The tool opens a local, read-only Math Workspace. Use its UI for source selection, definitions, and formulas.
- Text selections and formula popovers can add source attachments to the current conversation input. This does not automatically send a message. Selections are temporary; ongoing discussion, edits, and approvals stay in the native conversation.
- Prefer narrow tools over broad pasted context: `lookup_formal_object` for one stable object, `inspect_dependencies` for explicit strict relations, `lookup_knowledge` for maintained terms and notation, `inspect_lean_alignment` for observed Lean evidence, and `verify` for deterministic validation.
- Use `read_symbol_audit` only to inspect a cached report that the user already started in Math Workspace; it never initiates model work.
- Treat dependency, Lean, and audit results as evidence for discussion, not as automatic instructions to propagate edits or rewrite source.

For a new chapter, front matter, back matter, or continued page, read native project instructions and `.math-workspace/agent-guide.md` (refresh with the CLI's `prepare` if needed), and inspect `create-page --help` when needed. Use the supplied Node/CLI entry and working directory; do not assume a project npm script or global CLI is installed. In the Reader, “＋” reviews the title, kind, current book/volume, and read-only plan, then adds a request to the conversation input without sending it; without host support, copy the request.

Use `create-page --dry-run --json` first, then create with the reviewed `stateToken` as `--expect-state`. Refresh stale plans; if project, kind, title, container, and filePath are unchanged, use the new token. Review changed destinations or reuse existing manuscripts before proceeding. The helper assigns paths, order, and a stable page ID without overwriting source; write content into its returned file and run `finish` on that file. Multiple `front-matter/` and `back-matter/` pages keep the author's own titles and genres; `to-be-continued.md` is a separate page, and legacy intro/summary pages remain supported. Keep one Markdown source. Creation does not modify a saved publication plan; automatic plans discover matching structural pages when reviewed again. Merge relevant rules into existing project instructions when integration is requested; do not silently replace them or install skills.

For publication, maintain shared work metadata in `.math-workspace/config.json.metadata`, using the Reader's project metadata editor or this plugin's `publication metadata` / `publication save-metadata` commands with the current revision. Edition profiles store only overrides and edition identity; do not duplicate inherited authors, websites or repository URLs. New Reader plans automatically include structural prefaces, endings and numbered appendices within the selected books/volumes; CLI profiles opt in with `matter.automatic: true`. Existing plans keep their saved scope until explicitly enabled. Review the actual resolved metadata and page selection before building. Metadata or source changes require a fresh reviewed build; PDF/citation/Zenodo mappings use its frozen values. External DOI reservation, upload and publication still require their own authorization. A publication acknowledgement is separate from anonymous `publication verify-published` results; sandbox cannot establish production DOI resolution.
